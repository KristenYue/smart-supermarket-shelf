# 设计亮点

## 1. 可移植的 C++17 固件核心

货架 2 的业务判定从 Arduino 主循环中抽离到 `firmware/core/`。状态机以纯输入快照和阈值配置计算结果，不依赖 GPIO、Wi-Fi 或云服务，因此可以在 Windows 和 Linux CI 中直接编译测试。

状态优先级是显式业务规则：

```text
人工求助 > 遮挡异常 > 声音异常 > 无库存 > 低库存 > 正常
```

这避免了多个传感器同时异常时由 `if` 语句顺序偶然决定执行器行为。

## 2. 固定容量离线 Outbox

两套固件共享 `FixedOutbox<4, 96, 512>`：

- 编译期确定容量、主题和载荷上限；
- 不使用动态内存，降低长时间运行中的堆碎片风险；
- MQTT 发送失败或离线时入队；
- 队列满时丢弃最旧帧，并保留计数；
- 重连后按 FIFO 顺序恢复发送；
- 超长帧明确拒绝，不发生缓冲区越界。

## 3. 重启感知的 Telemetry v2

消息身份由 `deviceID + bootId + sequence` 组成。它同时覆盖四类常见 IoT 故障：重复投递、乱序到达、未同步时钟和设备重启。协议细节见 [Telemetry v2](TELEMETRY_V2.md)。

## 4. 边缘状态机与云端分析对齐

边缘设备负责需要低延迟的现场告警和执行器动作；Java 服务保存来源 `messageId`、`bootId` 和 `sequence`，进行查询与分析。两端采用相同的状态语义，使离线现场响应和在线运营视图保持一致。

## 5. 设备身份与最小权限链路

- ATECC608A/B 保存设备私钥；
- BearSSL 与 AWS IoT Core 建立 TLS 连接；
- 每台货架使用独立 Thing、Client ID 和证书；
- MQTT Topic 按设备划分遥测、事件、告警、命令和配置；
- Python 契约层拒绝未知设备、越权主题、控制字符和未声明配置字段；
- CloudFormation 使用 Thing policy variable 将 Client ID、证书绑定状态和 Topic 权限约束到同一 Thing；每台设备只能发布自身遥测/事件/告警，并只能订阅自身命令/配置。

## 6. 分层验证

| 层级 | 自动化证据 |
|---|---|
| C++ 固件核心 | 状态优先级、阈值边界、FIFO、溢出策略、超长帧 |
| Python 协议 | JSON 契约、命令/配置白名单、幂等、乱序、重启会话 |
| Java 云端 | 环境/库存分析、消息来源追踪、会话级顺序 |
| Spring 扩展 | 告警同步、接口参数、设备隔离、MySQL 存储适配 |
| 稳定性 | 固定随机种子注入重复与乱序，批量校验 50,000 条消息 |
